# 演習 8-C: パターン選択討議 (グループワーク・コードなし)

研修コース「LangChain による Agentic AI 開発実践」/ 第8章「マルチエージェント開発」/ 8-2 節

> **この演習はコードを書きません。** 5 つのデザインパターンの**定量比較**と**4 つの評価軸**を
> 根拠に、与えられたシナリオへ最適なパターンを選び、「なぜそれを選び、他を選ばないのか」を
> グループで議論して発表します (約 20 分)。

---

## 1. 演習の狙い (対応する章目標 2・3 / 分析・評価レベル)

- **章目標 2**: 5 つのデザインパターンを、公式の定量比較と 4 つの評価軸で比較できる
- **章目標 3**: 与えられたシナリオを分析し、トレードオフに基づいてパターンを選択し、根拠を説明できる

この演習のゴールは「唯一の正解を当てること」ではありません。**定量データを引いてトレードオフを
説明できること**、そして**採用しなかったパターンの理由まで言語化できること**が評価のポイントです。

| 評価項目 | 達成 (3点) | 一部達成 (2点) | 未達成 (1点) |
|---|---|---|---|
| 根拠の質 | 呼出回数・トークン・評価軸の定量データを引いて選択を正当化 | パターン選択は妥当だが根拠が定性的 | 根拠なし・特性の誤解がある |
| 比較の深さ | 採用しなかったパターンの理由も説明できる | 採用案の説明のみ | 比較ができていない |

---

## 2. 進め方

1. 3〜4 名のグループを作る (時間目安: 全体で約 20 分)
2. 下記シナリオ A〜D について、グループで 1 つずつパターンを選ぶ (5〜10 分)
3. 各シナリオの選択理由を、**§4 の定量比較表**と**§5 の評価軸**の数値・記号を引用して記録シート (§6) に書く (5 分)
4. 各グループが 1〜2 シナリオを発表し、選択と根拠を共有する (5 分)

> **議論のコツ**: 「このパターンが良い」だけでなく、「**他のパターンはこの数値が不利だから外した**」を
> 必ずセットで言うこと。それが分析・評価レベルの思考です。

---

## 3. 5 つのデザインパターン (1 行要約)

各パターンの動作原理は教材本文で確認済みの前提です。討議の手がかりとして 1 行要約を再掲します。

| パターン | 動作原理 (1 行要約) |
|---|---|
| **Subagents** | メインエージェント (supervisor) がサブエージェントを「ツールとして」呼ぶ。ルーティングはすべてメイン経由。サブは stateless |
| **Handoffs** | ツール呼び出しが状態変数を更新し、エージェントのふるまい (プロンプト・ツール) が動的に切り替わる。各担当がユーザーと直接対話 |
| **Skills** | 専門プロンプト・知識をオンデマンドで読み込む。単一エージェントが制御を保持し続ける (読み込んだ知識は会話に蓄積) |
| **Router** | 分類ステップが入力を仕分けて専門エージェントへ振り分け、結果を合成する。会話状態を持たない 1 回の分類 |
| **Custom workflow** | LangGraph で決定的ロジックとエージェント的ふるまいを混在させた独自フローを構築する |

> 本討議では、定量比較が提供されている **Subagents / Handoffs / Skills / Router** の 4 パターンから選びます
> (Custom workflow は「4 パターンに当てはまらない独自フロー」のための受け皿です)。

---

## 4. 定量比較 — 3 シナリオでのモデル呼び出し回数・トークン量

評価の物差しは 2 つです。

- **モデル呼び出し回数**: 多いほどレイテンシ (特に逐次実行) と API コストが増える
- **処理トークン量**: 全呼び出しを通じてコンテキストに載せた総量。多いほど処理コストとコンテキスト上限のリスクが増える

### 4-1. シナリオ 1: One-shot (単発の依頼)

> ユーザーが「コーヒーを買って」と 1 回だけ依頼。コーヒー専門のエージェント/スキルが `buy_coffee` を呼べる。

| パターン | モデル呼び出し回数 | 最適 |
|---|:---:|:---:|
| Subagents | 4 | |
| Handoffs | 3 | ✅ |
| Skills | 3 | ✅ |
| Router | 3 | ✅ |

> **読みどころ**: Subagents だけ 1 回多い。サブの結果が**必ずメインを 1 回経由して**ユーザーに届くため。
> これは欠陥ではなく「集中制御の対価」。

### 4-2. シナリオ 2: Repeat request (同じ依頼の繰り返し)

> 同じ会話で「コーヒーを買って」「もう一杯買って」と 2 回依頼。

| パターン | 2 ターン目の呼び出し | 合計 (2 ターン) | 最適 |
|---|:---:|:---:|:---:|
| Subagents | 4 | 8 (4+4) | |
| Handoffs | 2 | 5 (3+2) | ✅ |
| Skills | 2 | 5 (3+2) | ✅ |
| Router | 3 | 6 (3+3) | |

> **読みどころ**: **stateful** な Handoffs / Skills は 2 ターン目で引き継ぎ/再読み込みを省けて 40〜50% 削減。
> **stateless** な Subagents は 2 回目も同じ 4 回。Router も毎回分類し直すため 3 回。

### 4-3. シナリオ 3: Multi-domain (複数ドメインの統合)

> 「Web 開発の観点で Python・JavaScript・Rust を比較して」。各言語の知識が約 2,000 トークン。

| パターン | モデル呼び出し回数 | 総トークン量 | 最適 |
|---|:---:|:---:|:---:|
| Subagents | 5 | 約 9K | ✅ |
| Handoffs | 7+ | 約 14K+ | |
| Skills | 3 | 約 15K | |
| Router | 5 | 約 9K | ✅ |

> **読みどころ**: **並列実行できる** Subagents / Router が有利 (各担当が自分の 2,000 トークンだけを隔離
> コンテキストで処理)。Skills は呼び出し 3 回と最少だが、読み込んだ約 6K トークンが**以降の全呼び出しに
> 載り続ける**ため総トークンは約 15K に膨らむ。Handoffs は**逐次実行しかできず**最も不利。

### 4-4. サマリ (3 シナリオを 1 枚に)

| パターン | One-shot | Repeat request | Multi-domain |
|---|:---:|:---:|:---:|
| Subagents | 4 回 | 8 回 (4+4) | 5 回・約 9K トークン |
| Handoffs | 3 回 | 5 回 (3+2) | 7+ 回・約 14K+ トークン |
| Skills | 3 回 | 5 回 (3+2) | 3 回・約 15K トークン |
| Router | 3 回 | 6 回 (3+3) | 5 回・約 9K トークン |

> **すべてのシナリオで勝つパターンは存在しない**——これがこの表の最大のメッセージです。

## 5. 4 つの評価軸 (定性的な星取表)

| パターン | 分散開発 | 並列化 | マルチホップ | ユーザー直接対話 |
|---|:---:|:---:|:---:|:---:|
| Subagents | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐ |
| Handoffs | — | — | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| Skills | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| Router | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | — | ⭐⭐⭐ |

- **分散開発**: 別チームがコンポーネントを独立に保守できるか
- **並列化**: 複数エージェントを同時実行できるか
- **マルチホップ**: 複数のサブを直列に呼び継げるか
- **ユーザー直接対話**: サブ (担当) がユーザーと直接会話できるか

### 「何を最適化したいか」からの逆引き表

| 最適化したいもの | Subagents | Handoffs | Skills | Router |
|---|:---:|:---:|:---:|:---:|
| 単発リクエスト | | ✅ | ✅ | ✅ |
| 繰り返しリクエスト | | ✅ | ✅ | |
| 並列実行 | ✅ | | | ✅ |
| 大コンテキストのドメイン | ✅ | | | ✅ |
| シンプルな集中タスク | | | ✅ | |

## 6. 討議シナリオ A〜D と記録シート

各シナリオについて「選んだパターン」と「根拠 (§4 / §5 の数値・記号を引用)」「採用しなかったパターンの
理由」をグループで埋めてください。**検討の観点**を毎回チェックすると、根拠に厚みが出ます。

> **共通の検討観点**: ① ユーザーと直接対話し続ける必要はあるか ② 順序制約はあるか
> ③ 並列化の余地はあるか ④ 依頼は単発か繰り返しか ⑤ 各ドメインのコンテキストは大きいか
> そして「**要件が 1 つ変わったら (例: 会話が複数ターンになったら) 選択は変わるか?**」まで
> 考えられれば上級です。

### シナリオ A: 社内ヘルプデスクチャットボット (順序制約のある対話)

> 経理確認 → 申請内容確認 → 承認案内のように、**順序制約のある対話**でユーザーから段階的に情報を集める。
> 担当者が交代しながらユーザーと直接やり取りを続ける。

| 記入欄 | 内容 |
|---|---|
| 選んだパターン | |
| 根拠 (定量・評価軸を引用) | |
| 採用しなかったパターンの理由 | |
| 要件が変わったら? (例: 並列化が必要になったら) | |

### シナリオ B: 競合 3 社の調査レポート自動生成 (並列調査して統合)

> 各社のドメイン知識が大きく、**並列に調査して統合**したい。各社の調査は独立しており、
> ユーザーとの逐次対話は不要。

| 記入欄 | 内容 |
|---|---|
| 選んだパターン | |
| 根拠 (定量・評価軸を引用) | |
| 採用しなかったパターンの理由 | |
| 要件が変わったら? (例: 調査が単発でなく繰り返しになったら) | |

### シナリオ C: コーディングアシスタントへの専門能力のオンデマンド追加

> 1 つのコーディングアシスタントに、SQL や法務文書レビューなどの**専門能力を必要なときだけ追加**したい。
> ユーザーとの対話は途切れさせたくない。同じ会話で同種の依頼が繰り返されることも多い。

| 記入欄 | 内容 |
|---|---|
| 選んだパターン | |
| 根拠 (定量・評価軸を引用) | |
| 採用しなかったパターンの理由 | |
| 要件が変わったら? (例: 複数ドメインを並列に問い合わせたくなったら) | |

### シナリオ D: 情報源別の並列検索 (GitHub / Notion / Slack)

> 問い合わせを GitHub / Notion / Slack という**明確な情報源カテゴリに分類して並列検索**し、
> 回答を合成する。会話の継続は不要。

| 記入欄 | 内容 |
|---|---|
| 選んだパターン | |
| 根拠 (定量・評価軸を引用) | |
| 採用しなかったパターンの理由 | |
| 要件が変わったら? (例: 会話文脈を維持して複数ターン対応したくなったら) | |

---

## 7. 発表とふりかえり

- 各グループは担当シナリオの「選択 + 根拠 + 不採用理由」を 1〜2 分で発表します。
- 他グループと選択が割れた場合は、**どの数値・評価軸を重視したかの違い**を確認してください。
  選択そのものより「根拠の引き方」を比べることに価値があります。
- 想定解はこの場の討議で講師とともに導きます (この資料には記載していません)。
  「定量データで語れたか」「不採用理由まで言えたか」を自己評価して締めくくりましょう。
